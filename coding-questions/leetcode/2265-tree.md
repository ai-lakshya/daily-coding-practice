## 1. Premise

You are given the root of a binary tree. For **every** node, look at the
subtree rooted at that node (the node itself plus all of its descendants)
and compute the average of the values in it, **rounded down**. Count the
nodes whose own value equals that average.

**Constraints that matter:**

- `1 <= n <= 1000` — small. An `O(n^2)` solution passes. That matters
  because it means the problem is not testing whether you can find the
  linear solution, it is testing whether you can *express* a subtree
  computation cleanly.
- `0 <= Node.val <= 1000` — all values non-negative, so the maximum
  possible subtree sum is `1000 * 1000 = 10^6`. Comfortably inside `int`.
  Note this explicitly: it is the reason you never had to think about
  overflow here, and the reason you *will* have to in the next tree
  problem with `val <= 10^9`.
- The tree is not guaranteed balanced. A 1000-node path is legal input,
  so the recursion depth can be 1000.

**The reframing:** every node asks the same two questions about its own
subtree — *what is the sum* and *how many nodes* — and those two numbers
for a node are determined entirely by the same two numbers for its
children. That is the definition of a subproblem, so this is a recursion
that returns an aggregate rather than a recursion that just walks.

## 2. Concepts you need

### 2.1 The subtree as a subproblem

**What it is:** a rooted tree has the property that the subtree of a node
is itself a rooted tree, and the subtrees of the children are disjoint and
together cover everything except the node itself. That is *structural
recursion*: the data type is defined in terms of smaller copies of itself,
so a function over it can be too.

**How it works:** you define a function by a contract — "given a node,
`f(node)` returns X for the subtree rooted at that node" — and then you
write two things:

1. a **base case**, the answer for the empty tree (or for a leaf), and
2. a **combine rule**, the answer for a node written in terms of
   `f(node->left)` and `f(node->right)`.

You never reason about the whole tree. You reason about one node,
*assuming* the recursive calls already obey the contract. This assumption
is not hand-waving — it is induction on the height of the subtree, and the
base case is the induction's anchor.

For this problem the contract that works is:

```
f(node) = { sum of all values in the subtree, number of nodes in it }
```

with base case `f(nullptr) = {0, 0}` and combine rule

```
f(node) = { node->val + f(left).sum + f(right).sum,
            1        + f(left).count + f(right).count }
```

**When to reach for it:** the moment a problem asks something about *every
node's subtree*. The phrase "for each node, consider its subtree" in a
statement is a direct instruction to write a function with this shape.

**Worked micro-example** (deliberately not this problem — counting nodes):

```
        a
       / \
      b   c
         /
        d
```

`f(node) = number of nodes in the subtree`. Base `f(null) = 0`.
`f(b) = 1 + 0 + 0 = 1`. `f(d) = 1`. `f(c) = 1 + f(null) + f(d) = 2`.
`f(a) = 1 + f(b) + f(c) = 4`. Each node was visited once, and each node's
value used only its children's already-computed answers.

**Common mistakes:**

- Making the base case a *leaf* instead of `nullptr`. It works, but you
  then have to special-case "one child is null" separately, which is
  strictly more code and more branches to get wrong. `nullptr` as the base
  case absorbs both. (Your submitted code does the leaf version — see
  [§3.4](#34-your-submitted-solution-reviewed).)
- Forgetting that the subtree of a node **includes the node itself**.
  Every off-by-one in this family of problems is that.

**Sources:**

- [CP-Algorithms — Depth First Search](https://cp-algorithms.com/graph/depth-first-search.html)
- [Competitive Programmer's Handbook (CPH), ch. 14 "Tree algorithms"](https://cses.fi/book/book.pdf)

### 2.2 Postorder DFS

**What it is:** the three classic depth-first orders differ only in *when
you do the work for a node* relative to recursing into its children:

| order | work happens |
|---|---|
| preorder | before both recursive calls — node, left, right |
| inorder | between them — left, node, right |
| postorder | after both — left, right, node |

**How it works — and why postorder is forced here:** the work at a node
needs `f(left)` and `f(right)` to already be finished. Only postorder
guarantees that. Postorder is the order in which information flows *up*
the tree; preorder is the order in which information flows *down* it.

That is the general rule, and it is the single most transferable line in
this document:

> If a node needs data from its ancestors, push it **down** — preorder,
> pass it as a parameter. If a node needs data from its descendants, pull
> it **up** — postorder, return it from the call. If it needs both, you do
> two passes (that is rerooting).

**Complexity:** any DFS over a tree is `O(n)` time — every node and every
edge is touched a constant number of times — and `O(h)` extra space for
the call stack, where `h` is the height.

**When to reach for it:** "the answer at a node depends on its subtree" →
postorder. "the answer at a node depends on the path from the root" →
preorder.

**Common mistakes:** writing the node's work before the recursive calls
out of habit, then reading stale zeros out of the children.

**Sources:**

- [USACO Guide — Depth First Search](https://usaco.guide/silver/dfs)
- [CP-Algorithms — Depth First Search](https://cp-algorithms.com/graph/depth-first-search.html)

### 2.3 Subtree aggregation, and the redundancy it removes

**What it is:** the deliberate act of computing an aggregate (sum, count,
min, max, xor, "does this subtree contain a marked node") **once per
node** and carrying it upward, instead of recomputing it from scratch at
each node. On a tree this is exactly dynamic programming: overlapping
subproblems, solved bottom-up, each stored once.

**How it works:** think about what the naive version costs. If each node
walks its own subtree to find the sum, a node at depth `d` gets walked
once for each of its `d` ancestors plus itself. So the total work is

```
sum over all nodes v of (depth(v) + 1)
```

which is `O(n * h)`: `O(n log n)` on a balanced tree, and `O(n^2)` on a
path. Aggregation deletes exactly that factor of `h` by making each node's
contribution travel upward once, inside the return value, rather than
being re-fetched by every ancestor.

**Complexity:** `O(n)` time, `O(h)` space. Since you must at least read
every node to know its value, `O(n)` is the floor for this problem.

**When to reach for it:** whenever you notice the brute force re-walking
the same region of the tree. The signal is a loop over nodes with a
traversal *inside* it.

**Worked micro-example** (again, not this problem — subtree maxima on the
tree from §2.1, values `a=3, b=9, c=1, d=7`): `g(null) = -inf`,
`g(v) = max(v.val, g(left), g(right))`. Bottom-up: `g(b)=9`, `g(d)=7`,
`g(c)=max(1,-inf,7)=7`, `g(a)=max(3,9,7)=9`. Four nodes, four evaluations.
The brute force would have re-scanned `d` while handling both `c` and `a`.

**Common mistakes:** aggregating a quantity that is not actually
decomposable over children. Sum, count, min, max, xor, and gcd all
combine from children alone. "The median of the subtree" does not — it
needs the whole multiset, so the aggregate would have to *be* the
multiset, and the trick buys you nothing.

**Sources:**

- [CPH ch. 14.3 "Tree dynamic programming"](https://cses.fi/book/book.pdf)
- [USACO Guide — Depth First Search](https://usaco.guide/silver/dfs)

### 2.4 Returning several values from a recursion in C++

**What it is:** the combine rule here needs two numbers per node (sum and
count), so the recursive function has to hand back a pair of values. C++
gives you four ways, and they are not equivalent in cost.

**How it works:**

| form | cost per call | notes |
|---|---|---|
| `std::vector<int>` | a **heap allocation and free**, every call | never the right tool for a fixed-size tuple |
| `std::pair<int,int>` | free, register-sized | fine, but `.first` / `.second` do not say what they mean |
| a small `struct` | free, register-sized | named fields; the default choice |
| out-parameters (`int& sum, int& count`) | free | best when the "return" is an accumulation into shared state |

A `std::vector<int>` of three elements is 24 bytes of heap plus a control
block, allocated and destroyed once per node. The struct version passes in
registers. On `n = 1000` neither is observable, but the habit is worth
fixing while the stakes are zero — the same reflex on `n = 2 * 10^5` in a
contest is a real TLE.

There is a second, sharper reason to prefer the struct: `v[0]`, `v[1]`,
`v[2]` carry no type-checking and no meaning. Swap two of them and the
compiler is silent.

**When to reach for each:** a fixed set of named values → struct. A single
value plus a running answer that is not really "returned" anywhere → out
parameter or a member variable, which is the shape of
[§3.3](#33-optimal-v2--one-value-up-the-answer-on-the-side).

**Common mistakes:** returning a reference or pointer to a local struct.
Return by value; the compiler elides the copy.

**Sources:**

- [cppreference — Aggregate initialization](https://en.cppreference.com/w/cpp/language/aggregate_initialization)
- [cppreference — `std::vector`](https://en.cppreference.com/w/cpp/container/vector)

### 2.5 Integer division and floor

**What it is:** in C++, `/` on two integers performs **truncation toward
zero** (guaranteed since C++11), and `%` takes the sign of the dividend.
`std::floor` rounds toward negative infinity and returns a `double`.

**How it works:** for non-negative operands, truncation and flooring are
the same thing, so `a / b == floor(a / b)` and any call to `std::floor`
around an integer division is a no-op. They diverge for negatives:

```
 7 /  2  ==  3      floor( 7.0 / 2.0) ==  3
-7 /  2  == -3      floor(-7.0 / 2.0) == -4
```

There is also a trap independent of sign: `std::floor(a / b)` with `a` and
`b` both `int` computes the *integer* division first and then floors the
result, so the `floor` never sees the fractional part it was written to
handle. If you actually want a floating-point floor you must force the
conversion: `std::floor(static_cast<double>(a) / b)`. And once you do,
you have bought yourself `double` precision problems for free — above
`2^53` the division is no longer exact.

**When to reach for it:** when a problem says "rounded down" and the
values are non-negative, plain integer `/` **is** the answer. Reach for
`std::floor` only when a real `double` is involved, and for negative
integer operands use the standard floor-division idiom instead:

```cpp
int floor_div(int a, int b) { return a / b - ((a % b != 0) && ((a < 0) != (b < 0))); }
```

**Common mistakes:** exactly the one in your submission — `floor()` on an
integer expression. It is harmless here because values are non-negative,
but it reads as if it is doing something, which makes it worse than no
code at all.

**Sources:**

- [cppreference — Arithmetic operators (integer division)](https://en.cppreference.com/w/cpp/language/operator_arithmetic)
- [cppreference — `std::floor`](https://en.cppreference.com/w/cpp/numeric/math/floor)

### 2.6 Recursion depth on trees

**What it is:** each recursive call consumes a stack frame, so a DFS on a
tree of height `h` needs `O(h)` stack. A degenerate tree — every node
having one child — has `h = n`.

**How it works:** a typical frame in a function like this is on the order
of tens of bytes, and the default stack is 1 MB (MSVC) to 8 MB (Linux).
So depth 1000 is nothing, depth 10^5 is usually fine, depth 10^6 with a
fat frame is where stack overflow starts to happen — and it manifests as a
segfault / "runtime error" with no useful message, which is why it is
worth recognising by shape rather than by debugging.

**When to reach for the iterative form:** when `n` is large *and* the tree
can be a path (linked-list-shaped input, a "tree" built from a parent
array, a trie over long strings). See
[§3.5](#35-iterative-postorder-when-recursion-depth-is-a-real-risk).

**Common mistakes:** assuming the recursion is safe because the test cases
happen to be balanced.

**Sources:**

- [CPH ch. 14 "Tree algorithms"](https://cses.fi/book/book.pdf)

### 2.7 Complexity accounting for tree recursions

**What it is:** the habit of pricing a tree algorithm as *(work per node)
× (number of nodes)* rather than guessing from the shape of the code.

**How it works:** write down what a single call does *excluding* its
recursive calls. Here that is a constant number of additions and one
comparison, so `O(1)` per node and `O(n)` total. In the brute force, a
single call does a full subtree walk, so the per-node cost is
`O(size of subtree)` and the total is the sum of all subtree sizes, which
equals the sum of all depths — `O(n*h)`.

That last identity is worth memorising, because it is the standard way to
price "every node looks at its whole subtree":

```
sum of subtree sizes  ==  sum over nodes of (depth + 1)
```

`O(n log n)` when balanced, `O(n^2)` on a path.

**When to reach for it:** any time you are tempted to describe a nested
tree traversal as "O(n log n) because trees are logarithmic". Trees are
only logarithmic when something guarantees they are balanced, and a raw
binary tree from an input array guarantees nothing.

**Common mistakes:** counting the `O(h)` stack against the time bound, or
forgetting it in the space bound.

**Sources:**

- [CPH ch. 14](https://cses.fi/book/book.pdf)
- see also [cq-006 §2.3 "complexity accounting"](../contests/abc-475/e.md#23-complexity-accounting-cost-the-whole-query-not-the-clever-part)

## 3. The solutions, brute force to optimal

**The insight:** a node's verdict needs two numbers about its own subtree,
and both are sums over the children. So one postorder pass that returns
`{sum, count}` answers the question for *every* node at once.

**How you would get there:** start from the definition literally — "for
each node, average its subtree" — and write that. Then notice that the
inner walk at a node re-visits every node the walk at its parent will also
visit, and that the parent's sum is just its own value plus the two
children's sums. The moment you can write the parent's aggregate in terms
of the children's, the outer loop disappears.

### 3.1 Brute force — recompute each subtree

The direct transcription of the statement. For every node, walk its
subtree and total it up.

```cpp
class Solution {
public:
    // Accumulate the subtree of `node` into sum/count.
    void collect(TreeNode* node, int& sum, int& count) {
        if (node == nullptr) return;
        sum += node->val;
        ++count;
        collect(node->left, sum, count);
        collect(node->right, sum, count);
    }

    int averageOfSubtree(TreeNode* root) {
        if (root == nullptr) return 0;

        int sum = 0, count = 0;
        collect(root, sum, count);

        int here = (root->val == sum / count) ? 1 : 0;
        return here + averageOfSubtree(root->left)
                    + averageOfSubtree(root->right);
    }
};
```

**Complexity:** time `O(n*h)` — `O(n log n)` balanced, `O(n^2)` on a path
(`10^6` operations at `n = 1000`, so it passes here). Space `O(h)`.

**Why it is worth writing anyway:** it is correct, it takes ninety seconds,
and it is the thing you diff the fast version against on a random-tree
stress test. In a contest with these constraints you would submit it.

**What kills it:** raise `n` to `10^5` and the path case becomes `10^10`
operations. The waste is fully visible in the code — `collect` at a node
and `collect` at its parent walk the same nodes.

### 3.2 Optimal — one postorder pass returning an aggregate

Replace "ask each node to go find its subtree" with "have each subtree
hand its summary to its parent".

```cpp
class Solution {
    struct Agg {
        int sum;    // total of every value in this subtree
        int count;  // number of nodes in it
    };

    int answer = 0;

    Agg dfs(TreeNode* node) {
        if (node == nullptr) return {0, 0};      // base case absorbs missing children

        Agg l = dfs(node->left);
        Agg r = dfs(node->right);

        Agg here{node->val + l.sum + r.sum, 1 + l.count + r.count};

        // count >= 1 always, so the division is safe; both operands are
        // non-negative, so truncation is the required floor.
        if (node->val == here.sum / here.count) ++answer;

        return here;
    }

public:
    int averageOfSubtree(TreeNode* root) {
        answer = 0;
        dfs(root);
        return answer;
    }
};
```

**Correctness argument:** by induction on subtree height. For height 0
(`nullptr`) the returned `{0,0}` is trivially the sum and count of an empty
subtree. For a node, assume both calls returned correct aggregates for the
children's subtrees; the subtrees of the two children and `{node}` are
disjoint and cover the node's subtree exactly, so `here.sum` and
`here.count` are correct. The verdict for the node is then evaluated
against correct values, and `answer` is incremented at most once per node,
so it ends as the count of qualifying nodes.

**Complexity:** time `O(n)` — one visit per node, `O(1)` work each. Space
`O(h)` for the stack. `O(n)` time is the floor: you cannot decide a node's
verdict without reading every value beneath it.

### 3.3 Optimal v2 — one value up, the answer on the side

Same algorithm, different plumbing. Worth seeing because the tradeoff
recurs constantly.

```cpp
class Solution {
    int answer = 0;

    // returns {sum, count}; `answer` accumulates as a side effect
    std::pair<int,int> dfs(TreeNode* node) {
        if (node == nullptr) return {0, 0};
        auto [ls, lc] = dfs(node->left);
        auto [rs, rc] = dfs(node->right);
        int sum = node->val + ls + rs, count = 1 + lc + rc;
        if (node->val == sum / count) ++answer;
        return {sum, count};
    }

public:
    int averageOfSubtree(TreeNode* root) { answer = 0; dfs(root); return answer; }
};
```

versus carrying the count *in* the return value, as your solution does:

```cpp
struct Agg { int sum, count, good; };   // `good` = qualifying nodes in this subtree

Agg dfs(TreeNode* node) {
    if (node == nullptr) return {0, 0, 0};
    Agg l = dfs(node->left), r = dfs(node->right);
    int sum = node->val + l.sum + r.sum;
    int count = 1 + l.count + r.count;
    int good = l.good + r.good + (node->val == sum / count);
    return {sum, count, good};
}
```

**Which to prefer:** the three-field version is *pure* — no shared mutable
state, so it composes and is trivially parallelisable. The
member-variable version is shorter and is what most editorials write. Both
are `O(n)`. The pure version is the better habit for anything you may
later want to memoise or reuse; carrying the answer in the aggregate is
also what you need if a later variant asks for the count *per subtree*
rather than a global total.

### 3.4 Your submitted solution, reviewed

**What you did:** exactly §3.3's three-field form — a DFS returning
`{sum, count, ans_count}` with the answer carried up in slot 2. The
algorithm is right and the complexity is right. This is the intended
solution.

**What holds up:**

- The aggregate is the correct one, and the combine rule is correct,
  including the fact that a node's `ans_count` sums its children's.
- The header comment states the idea in one line. Keep doing that.
- No overflow: max sum `10^6`, well inside `int`. You did not say so, but
  the choice is right.

**What does not:**

- `floor(rootVal / rootCount)` — `rootVal` and `rootCount` are both `int`,
  so `rootVal / rootCount` is *already* an integer division that truncates.
  `floor` then rounds an integer, which does nothing, and it does it by
  converting to `double` and back. It is a no-op that reads like a
  correctness measure, and the `static_cast<int>` around it exists only to
  undo the `double` that `floor` introduced. All three should be deleted:
  `root->val == rootVal / rootCount`. (Concept: [§2.5](#25-integer-division-and-floor).)
  This also lets you drop `#include <cmath>`.
- The leaf special case on line 27 is dead weight. With the `nullptr` base
  case returning `{0,0,0}`, a leaf falls out of the general path correctly:
  `sum = val`, `count = 1`, `val == val/1` → `good = 1`. Same answer, one
  fewer branch, one fewer place for a bug.
- `std::vector<int>` as the return type heap-allocates per node, and
  `std::vector<int> emptyAns{0,0,0}` constructs a fresh vector *per call*
  just to represent "no child". A three-field struct is free and names its
  fields. (Concept: [§2.4](#24-returning-several-values-from-a-recursion-in-c).)
- `dfs(root)` is called unconditionally, so a `nullptr` root would
  dereference. LeetCode guarantees `n >= 1` here, so it cannot fire — but
  the `nullptr` base case makes it a non-issue for free.

**Idiomatic notes:**

- `leftVal[0]`, `leftVal[2]` — positional access with no type safety.
  `l.sum`, `l.good`.
- `auto rootIsValidAns = ...` gives a `bool` named as if it were a noun;
  either fold it into the `if` or name it `rootQualifies`.
- The ternary `rootIsValidAns ? 1 + l.good + r.good : l.good + r.good` is
  `l.good + r.good + rootQualifies` — a `bool` promotes to `0` or `1`.

Net: the thinking was right, the packaging cost you four avoidable lines
and a per-node allocation. §3.3's second block is your solution with those
removed.

### 3.5 Iterative postorder, when recursion depth is a real risk

Not needed at `n = 1000`. Worth having the shape in your fingers for the
version of this problem with `n = 10^6`.

```cpp
int averageOfSubtree(TreeNode* root) {
    // node -> {sum, count}; operator[] default-constructs {0,0}, which
    // conveniently makes the nullptr lookup the base case.
    std::unordered_map<TreeNode*, std::pair<int,int>> agg;
    std::vector<std::pair<TreeNode*, bool>> stack{{root, false}};
    int answer = 0;

    while (!stack.empty()) {
        auto [node, childrenDone] = stack.back();
        stack.pop_back();
        if (node == nullptr) continue;

        if (!childrenDone) {
            stack.push_back({node, true});          // revisit after the children
            stack.push_back({node->left, false});
            stack.push_back({node->right, false});
        } else {
            auto [ls, lc] = agg[node->left];
            auto [rs, rc] = agg[node->right];
            int sum = node->val + ls + rs, count = 1 + lc + rc;
            agg[node] = {sum, count};
            if (node->val == sum / count) ++answer;
        }
    }
    return answer;
}
```

The `bool` flag is the general trick for turning any postorder recursion
iterative: push each node twice, and do the node's work on the second pop,
by which time both children have been fully processed.

**Complexity:** time `O(n)` expected (hash lookups), space `O(n)` — worse
than the recursive version's `O(h)`, which is the price of not using the
call stack. On a tree with node ids you would use a `vector` instead of an
`unordered_map` and get `O(n)` worst case.

`root = [4,8,5,0,1,null,6]`, expected answer `5`.

```

     / \    \
```

Postorder visits `0, 1, 8, 6, 5, 4`:

| node | l.{sum,count} | r.{sum,count} | sum | count | sum/count | val | qualifies |
|---|---|---|---|---|---|---|:--:|
| 0 | {0,0} | {0,0} | 0 | 1 | 0 | 0 | yes |
| 1 | {0,0} | {0,0} | 1 | 1 | 1 | 1 | yes |
| 8 | {0,1} | {1,1} | 9 | 3 | 3 | 8 | no |

| 5 | {0,0} | {6,1} | 11 | 2 | 5 | 5 | yes |

Five qualifying nodes. Note node `5`: `11/2 = 5.5` truncates to `5`, which

### 3.7 Edge cases the code handles

- **`n = 1`** — the root is a leaf, `sum/count = val/1 = val`, answer `1`.
  This is LeetCode's second sample.
- **One-sided children** — the `nullptr` base case returns `{0,0}`, which
  is the identity for both `+` on sums and `+` on counts, so a missing
  child contributes nothing without any branch.
- **All zeros** — every node has `sum = 0`, `count >= 1`, `0/count = 0`,
  so every node qualifies. A good manual test that the division is not
  dividing by zero anywhere.
- **Division by zero** — impossible: `count >= 1` at any real node,
  because the node counts itself. The division is only ever evaluated at a
  non-null node.
- **Overflow** — not reachable at `val <= 1000, n <= 1000`. If `val` were
  `10^9`, `sum` would need `long long`; the comparison `node->val == sum /
  count` would still be fine because the quotient is back in range.

---

## 4. Takeaways

- **Information flowing up the tree is a postorder return value;
  information flowing down is a preorder parameter.** Deciding which
  direction a problem needs is usually the entire design step.
- **A brute force that re-walks a subtree at every node costs `O(n*h)`,
  and `sum of subtree sizes == sum of depths`.** Recognise that sum — it
  is how you price this family of solutions without guessing.
- **Base the recursion on `nullptr`, not on leaves.** The empty tree is
  the identity element for every aggregate you will ever combine, so it
  deletes the one-child special case for free.
- **`std::floor` on an integer division does nothing.** Integer `/` already
  truncates, and truncation is floor for non-negative operands.
- **A fixed-size tuple returned from a hot recursion is a `struct`,
  never a `std::vector`.** One heap allocation per node is invisible at
  `n = 1000` and fatal at `n = 10^6`.
